# 模拟面试：需求盘点（D-1）

> **状态：盘点中，未立项。** 本文件不是 feature 文件，不锁定实现，也不产生交付承诺。
> 目的：把已经写下来的需求归位，把真正未决的问题列清楚。§4 的阻塞项没有结论之前，不进入 D0。

盘点日期：2026-10-01

## 1. 结论

需求大约写了 **80%**，但散落在两类"不能直接实施"的位置：

| 出处 | 内容 | 为什么不能直接用 |
|---|---|---|
| `docs/design/visuals/`（4 份稿） | 四个页面的信息架构、报告层级、Agent 状态机与不变量 | 是**已确认的设计**，但不含数据契约与验收标准 |
| 旧 change `deliver-probeinterview-mvp` | 7 份 spec / 741 行 / **60 条 Requirement** | 整份被列为"被否定的参考"：需求可追溯，技术方案已否 |

关键事实：**旧设计自己的 `Open Questions` 只有两条**，都是"实现时再选供应商"。也就是说
产品决策当初是定完的，**被否的是技术方案**。现在缺的一步是把这两者分开——
保留需求、丢弃方案，并逐条对照现在的 ADR 重新确认。

## 2. 已经定下来的

### 2.1 页面与交互（视觉稿，已确认）

| 页面 | 已定的内容 |
|---|---|
| 模拟配置 | 简历（PDF，可更换，显示"已解析 N 个项目 / M 项技能"）、工作年限、目标公司（可选）、JD 截图（可选）、面试语言、时长 15/30/45、确认并开始 |
| 面试过程 | 当前知识点标签、题号、剩余时间、文字问题 + 追问、按住录音、**每题最多 3 次录制** |
| 转写确认 | 转写文本**不可直接编辑**、剩余录制次数、重新录制 / 确认并继续 |
| 结果报告 | 总分、年限基线、五维能力、证据覆盖率、逐题记录、回答评估（知识点级命中/遗漏 + 回答原文引用）、复盘**完全可选** |

### 2.2 Agent 行为（`interview-agent-state-machine.html`，已确认）

生命周期 `configured → in_progress → finalizing → completed`；`in_progress` 内部循环
`question.displayed → 录音与 ASR → 用户确认转写 → 过程证据评分 → 覆盖与时间决策 → 下一动作`；
动作只有三种：继续追问 / 切换知识点 / 结束面试。

五条不变量：**确认后不可变**、**评分必须引用证据**、**面试结束前不显示分数**、
**音频是临时的**（重录与确认时主动删除）、**历史结果永久引用当时的版本快照**。

失败态：`awaiting_transcript_confirmation`、`scoring_turn`、`failed_recoverable`、
`ended_early`、`failed_terminal`。同步关键路径 = 展示问题 / 转写确认 / 过程评分 / 下一问；
最终报告、Embedding、删除重试可以异步。

## 3. 需要"保留需求、重新确认方案"的地方

旧 spec 写于当前 ADR 之前（ADR 0001–0006 是之后立的），以下是已知冲突：

1. **私人题库**：旧 spec 有（占 20% 题量）。`knowledge-upload-mvp-overview.md` 明确写着
   "私人题库、知识卡片生成、学习进度、模拟面试和面试报告不属于本 MVP"。两处直接矛盾。
2. **身份与能力**：旧 spec 是"微信允许名单"；现在是 `ActorContext(actor_id, capabilities)`（ADR 0004）。
3. **API 约定**：旧 spec 没有 RFC 9457 Problem Details、202 + Location、Idempotency-Key 这些现行约束。
4. **异步架构**：OCR / LLM 调用要和 ADR 0003 的 Celery 任务模型对齐，旧 spec 没写这一层。
5. **五维权重**是否仍然照旧（15/25/20/25/15）——它写进评分规则版本，是一项产品决策，不是实现细节。

## 4. 真正未决的

### 4.1 平台核心内容从哪里来（阻塞其余一切）

评分按知识点、复盘按稳定知识点 ID、50% 题量来自"平台公共核心"，所以面试**必须有**一份
带稳定知识点 ID 的、版本化的内容包（知识点 + 题）。

`core-content-management` 说它由 XMind/Markdown 一次性导入产生，**不需要在线 CMS，
也不需要"用户上传 → 解析 → 关联 → 审核"那条 Later 管线**。

所以 `mvp-roadmap.md` 依赖图里"模拟面试排在整条知识管线之后"这条链，比看上去松：
真正的最小依赖是**一份平台内容导入包 + 一套稳定知识点 ID**，不是 Later 里的六项。

需要你决定：**是否接受先立一套最小知识点分类**（后面再和 `establish-role-knowledge-topics`
的六主题对齐），而不是等整条管线。

### 4.2 其余未决项

- 私人题库到底在不在 MVP 里（见 §3.1）。
- 复盘与知识卡片的耦合深度：`review-management` 假设存在"用户知识卡片"，而知识卡片属于私人学习库，
  那部分同样被 `knowledge-upload-mvp-overview.md` 移出 MVP。
- 报告里"实际题目来源比例"要不要对用户可见（旧 spec 要求展示）。

## 5. 未验证的外部能力（L3 候选）

| 能力 | 为什么是 L3 | 卡住什么 |
|---|---|---|
| 简历 PDF 解析 | 无选型、无质量基线 | 决定"简历技术路线"那 30% 题量能否成立 |
| JD 多图 OCR | 同上 | 决定 JD 优先级的可靠性 |
| 语音转写（ASR） | 同上；还牵涉成本、延迟与音频即时删除 | 决定整条回答链路 |
| 结构化出题（受控知识点 ID + Schema 校验） | 未验证 | 决定"不是自由聊天机器人"这条原则能否成立 |
| 五维评分校准 | 未验证；旧设计自己把它列为风险（单一 Agent 自洽偏差） | 决定报告是否可信 |

## 6. 最小可验证切片（**建议，待确认**）

一次 15 分钟、只用 JD 的面试：配置快照 → 3–5 题结构化出题 → 回答（可先用文字代替录音）
→ 每题过程评分（必须引用证据）→ 最终五维校准 → 报告。

明确不做：复盘、知识卡片、私人题库、回放界面、离线评估。
