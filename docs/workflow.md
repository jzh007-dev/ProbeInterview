# 开发工作流（D0–D6）

替代原 OpenSpec 流程。原则：**规划一页纸，验收变测试名，判卷交给机器。**

## 为什么是这套流程（实测成本模型）

样本：一轮 4 个 bug 的修复，147 次模型往返、30.3 分钟墙钟。

- **61% 的时间是"往返税"**——输出不足 100 token 的往返平均 7.6 秒，147 次就是 18.6 分钟。
  决定耗时的是**往返次数 × 固定开销**，不是探索、文档或上下文大小。
- **99.85% 的 token 花在输入上**（29,937,066 in / 41,500 out = **721 : 1**）。
  输入 = 往返次数 × 上下文。该轮上下文从 164k 涨到 239k，而**新会话起步只要 23.5k**。
- 昂贵的是**诊断**，不是改动量：该轮后端 500 占 70 次往返；两个纯 UI bug 只占 31 次，
  却因为背着 229k 上下文烧掉 7.10M 输入 token——放到新会话里做只要约 0.93M（**−87%**）。

后面各节都是这三条纪律的展开：

1. **一个交付单元 = 一个会话**，不要连做——后面的单元会替前面的背上下文。
2. **诊断与实施分成两次交接**。
3. **少一次往返就是省一笔钱**：能并行的读取合并成一条命令，同一文件的多个区间一次读完。

**自查**：`scripts/session-cost` 按会话打印调用次数、输入:输出、平均与峰值上下文。
看 **输入:输出** 那一列——它不受任务大小影响：`< 40:1` 健康，`40–100:1` 上下文偏大，
`> 100:1` 大概率在打转（同一个错误反复试）。

## 流水线

| 阶段 | 产物 | 放在哪 | 何时执行 |
|---|---|---|---|
| **D-1 需求盘点** | 已定 / 未定清单（不是完整 PRD） | `docs/requirements/<name>.md` | **范围还没定时**。不锁定实现，不产生交付承诺 |
| D0 范围 | feature 一页纸：为什么 / 范围 / 不做 / **落点** | `docs/features/<name>.md` | 动笔前，15 分钟，**由人填** |
| D1 接口设计 | §接口 端点表 → Pydantic contracts | feature 文件 + `contracts.py` | 写实现之前；契约先于代码 |
| D2 单测 | 行为命名用例，每条 §验收 对应一个测试名 | `tests/unit` | 随实现，pre-commit 判卷 |
| D3 集成 | 真实 PG/Redis 行为、并发、迁移 | `tests/integration` | `scripts/verify --full` |
| D4 拓扑 | 整链路 Compose 断言 | `scripts/test-compose-topology` | 合并前 / CI |
| D5 真机 β | automator 能表达的 → beta smoke；其余 → §真机验收清单 | feature 文件 + `scripts/test-beta-smoke` | 功能"完成"后、发布前 |
| D6 部署验证 | 部署清单 + 回滚 | `docs/ops.md` | 每次上线 |

## 交接点

1. 一个**交付单元** = 一个提交 = 一次交接。大小 ≈ 人能在一个坐姿里审完（≤500 行 diff）。
2. 单元做完就提交，然后**停下**：给出 diff 摘要、验收条目对照、原始验证输出，等 review。
   "连做下一个单元"是违规，不是勤奋。
3. **一次会话只做一个单元。** 跨单元的上下文继承是实测里最贵的一项开销。
4. 跨会话接手读 feature 文件 §当前中间态，**不要从 `git log` 反推**；会话结束前更新它。
5. §落点 由人在 D0 填。填不出落点就不要开工，说明范围还没想清。
6. 停下时按固定五段汇报，缺一不可：

```text
Changed:       <改了哪些文件>
Checked:       <实际跑过的命令 + 原始输出>
Not checked:   <没验证什么，为什么>
Next decision: <需要你定的那一件事，没有就写 none>
Recovery:      <这个单元错了怎么撤>
```

`Not checked` 是必填项。空着不等于"没有遗漏"，只等于"漏了没写"——实测里那次
`scripts/verify --full` 明确点名却没跑，就是缺这一段。

## D-1 需求盘点（范围还没定时用）

D0 要求你填得出 §落点。填不出来，说明需求还没成型——这时**不要建 feature 文件**，
先做 D-1。产物不是完整 PRD，而是一份**已定 / 未定清单**：

1. **已定**：写下来的决定，带出处（哪份视觉稿、哪份旧 spec、哪条 ADR）。
2. **需要重新确认**：写下来了、但写在当前 ADR 之前因而可能冲突的部分。
3. **真正未定**：需要人拍板的决策，按"卡住了谁"排序。
4. **未验证的外部能力**：转成 L3 spike 的候选。
5. **最小可验证切片**：能把上面三项里最不确定的那项先验证掉的最小范围。

规则：

- 时间盒。盘点的是"已经写了什么"，不是重新设计。
- 未定清单里存在阻塞项时，不得进入 D0 立项。
- 盘点结论只写证据与问题，**不要替人回答未定项**。

> 原 OpenSpec 的 explore 占的就是这个位置。它被删掉的是四份工件的仪式感，不是这项活动本身。

## 两阶段：诊断 → 实施

适用于 bug 修复、行为不符合预期、以及任何"该改哪里还不确定"的工作。

**阶段一 · 诊断**（用强模型）

- 输入：症状（报错、URL、截图、复现步骤）+ `docs/recipes.md` §0 落点索引。
  **不要**让它先读 feature 文件和 `git log` —— 那是重新推导状态，实测里最浪费的一段。
- 产物固定成这个样子，不是散文：

```text
根因：<一句话>
落点：
| 文件 | 改什么 | 验证 |
不碰：<明确列出不改的>
验证命令：<具体命令>
```

- **停下等确认。** 审这张表约 1 分钟；方向错了，损失是一次诊断而不是一整轮实现。
- 预算：超过约 25 次往返还没定位到根因，停下汇报"已经排除了什么"，不要继续加实验。
- **同一个错误试两次就停。** 列出 3–5 个可能原因，用手上已有的证据对比，挑最便宜、能用一条命令证伪的那个。反复 `git stash`、起临时容器、重跑整套测试是症状不是方法；要回答"改之前坏不坏"，用一条查询、一个最小测试，或 `git show HEAD:<file>`。

**阶段二 · 实施**（用便宜模型）

- 输入：上面那张表 + "只改列出的文件"。
- 不许重新诊断；需要改表就先停下。
- 完成条件见 §完成的定义。

**模型分配要反着直觉**：强模型放阶段一，便宜模型放阶段二。成本 = 往返次数 × 上下文，
弱模型多绕 30 次往返就多约 6M 输入 token——比它省下的单价贵得多。

## 验证分级（按改动类型）

按**改动类型**定深度，按**规模**（L1/L2/L3）定要不要 `--full`。两条轴分开算。

| 改动类型 | 至少跑 |
|---|---|
| 文档 / 注释 | 格式检查 + `git diff --check`；改到了命令示例就真跑一遍 |
| 代码 | `scripts/verify`；合并门槛加 `scripts/verify --full` |
| 配置 / 迁移 / Compose / 拓扑 | 上一行 + `scripts/test-compose-topology` |
| 小程序页面或组件 | 上一行 + `cd apps/miniprogram && npm test && npm run typecheck` |

已记录的浪费：一次纯文档提交后又跑了一次 `--full`，约 3 分钟 Docker 换来零信号。

## 会话开场模板（填四个空）

```text
本次单元：<编号+名字>，见 docs/features/<name>.md §交付单元。
落点、不变量、验收条目都在那一节；只读 §落点 列出的文件，不做全仓检索。
做完一个提交就停下：贴 git diff --stat、验收条目对照和原始验证输出，等我 review，
不要开始下一个单元。
验证：scripts/verify。
```

反例（用过，不要再用）：「先读该文件和 git log 了解已完成部分」——这句话本身就在要求
agent 重新推导状态，是跨会话重复探索的直接来源。

## 完成的定义（合并门槛）

1. `scripts/verify --full` 全绿，且**原始输出被贴出来**（不许 `>/dev/null`）；
2. feature 文件 §验收 每条都有对应测试（测试名即凭证）；
3. §真机验收清单 勾完（有 UI 的 feature）；
4. 每个交付单元都在 review 通过后才进入下一个；
5. `git status` 只剩预期的未跟踪文件。

D6 是部署的门，不是合并的门。

## 规模分级（一页纸不够时怎么办）

| 级别 | 进入信号 | 做法 |
|---|---|---|
| **L1 默认** | 单模块、≤1 张新表、验收 ≤10 条 | 一页纸 feature，直接实现 |
| **L2 跨模块 / 新数据真相** | 涉及 ≥2 个模块、新表或新端口、验收 >10 条、需要异步/补偿流程 | feature 文件允许增加"设计"小节（上限 2 页，只写结构、数据模型、时序、失败路径，不复述架构文档）；涉及技术栈/模块边界/数据归属的决策**先写 ADR**；范围过大时在 BACKLOG 拆成 2–4 个子 feature 串行实现，父 feature 文件只留总览和链接 |
| **L3 技术不确定** | 依赖未验证的外部能力（LLM 生成质量、语音转写、评分可信度） | 先做时间盒 spike（throwaway，不进 main），结论写回 BACKLOG，再按 L1/L2 立项 |

判断顺序：先看是不是 L3（风险），再看是不是 L2（规模），默认 L1。禁止把 L2 写成一页纸硬塞——验收清单超过 10 条还没拆，就是信号。

分级同时决定**交付单元的数量**：L2 必须显式列出 §交付单元，L1 可以在实现中顺手提交。

## 规则

- **需求来源**：只从 `BACKLOG.md` 领活。一次会话只做一个**交付单元**（不是"一个 feature"，也不是"一个验收条目"）。
- **β case 规则**：能用 `miniprogram-automator` 表达的用例必须自动化进 smoke，不许留人工；人工清单只收真机微信运行时、真实设备存储/网络、真实 OSS 三类。人工清单保持每个 feature ≤5 条。
- **提交**：每个交付单元一提交，提交前 `scripts/verify` 必须绿（pre-commit hook 强制）。禁止"攒一批"提交；实测里 5 个提交在 3.5 分钟内集中落地，等于没有交接点。
- **偏离设计**：直接改 feature 文件相应小节并继续，不需要停下来等人批准；但涉及技术栈、模块边界、数据真相归属的，必须先写 ADR。
- **测试分层**：unit 测不变量与纯逻辑（秒级）；integration 测真实 PG/Redis/迁移/并发；jest 测小程序 model/service/组件逻辑；smoke 只测"活着的链路"，不测业务细节。
- **测试命名**：`test_<行为>_when_<条件>`，对应 feature 验收条目，让测试名可当作需求清单读。

## 规划文件的位置与流向

做一个新需求的完整路径：

```text
⓪ 需求盘点     docs/requirements/<name>.md           （仅当范围还没定；产物是已定/未定清单）
① 排期入册     BACKLOG.md                          （加一行到 Next 或 Later）
② 立项一页纸   docs/features/<kebab-name>.md       （cp docs/features/_template.md，
                                                    填：为什么/范围/不做/落点/接口/验收/交付单元）
③ 架构级决策   docs/adr/NNNN-xxx.md                （仅当改技术栈/模块边界/数据归属；
                                                    同步 docs/architecture.md）
④ 按单元实现   prompt 用 §会话开场模板 指向一个交付单元；做完一个停下等 review
⑤ 会话交接     更新 feature 文件 §当前中间态
⑥ 完成归档     移入 docs/features/done/            （git 历史 + 测试名即完整档案）
```

| 文件 | 管什么 | 何时写/改 |
|---|---|---|
| `BACKLOG.md` | 做什么、什么顺序 | 立项时加行，做完划掉 |
| `docs/requirements/<name>.md` | 范围还没成型时的已定/未定清单 | D-1 时建；立项后不再更新，转由 feature 文件接手 |
| `docs/features/_template.md` | 新 feature 文件的模板 | 模板本身演进时才改 |
| `docs/features/<name>.md` | 单个功能的范围、落点、契约、验收、交付单元、当前中间态 | 立项时建；偏离设计时随手改；每次会话结束更新中间态 |
| `docs/features/done/` | 完成功能的归档 | 功能合并后移入 |
| `docs/architecture.md` + `docs/adr/` | 项目级结构与技术决策（ADR 只追加） | 架构决策落地时 |
| `docs/recipes.md` | 怎么写：接口/表/页面的标准做法 + 落点索引 | 出现新模式时补一条；发现 agent 重复探索同一个地方时补一条 |
| `docs/workflow.md` | 本文件：过程、门槛与文件流向 | 流程变化时 |
| `docs/ops.md` | 部署与上线验证 | 拓扑变化时 |
| `docs/development.md` | 本地启动与手工命令 | 命令变化时 |
| `openspec/` | **冻结的历史归档**，不再更新 | 永不 |

与旧 OpenSpec 工件的对应关系（仅供翻阅 `openspec/` 归档时对照）：

| 旧工件 | 新去处 |
|---|---|
| `proposal.md` | feature 文件 §为什么 + §范围 |
| `design.md` | §接口表 + §落点 + §验收失败路径 + §决策（超 2 页 = L2，拆阶段） |
| `tasks.md` | §交付单元（只列可提交的单元，不列实现内部步骤） |
| `specs/` delta | 取消——测试名即规格，CI 保证不漂移 |
| 归档仪式 | 移入 `docs/features/done/` |
