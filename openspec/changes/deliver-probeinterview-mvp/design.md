# Design

## Context

项目当前是绿地，仅存在 OpenSpec 规划文件，没有既定代码结构或技术栈。MVP 运行在微信小程序中，面向指定微信身份开展单用户封闭试用，但数据模型需要保留未来多用户迁移所需的用户和归属字段。

小程序不适合承担长耗时的文件解析、OCR、语音转写、LLM 编排和离线评估，因此客户端只负责交互与临时文件上传，所有领域状态、评分、版本和 Trace 均由后端持久化。外部模型、OCR 和语音服务尚未选定，设计需通过适配器隔离供应商差异。

本设计以已确认的 `proposal.md` 和已同步的 delta specs 为 MVP 范围与验收基线。

## Goals / Non-Goals

**Goals:**

- 用一个可部署的端到端架构连接平台内容导入、个人学习、模拟面试、证据评分、短板复盘和最小 Trace。
- 在线只使用一个面试 Agent，同时保留以后引入证据图、重放和评分漂移分析所需的数据。
- 将 LLM 输出限制为结构化、可校验、可引用证据的结果，避免模型直接控制持久化关系。
- 确保简历、JD、回答和私人题库默认私有，且原始录音在确认转写后立即删除。
- 让模型、Prompt、评分规则、平台内容和评估集均可版本化，以支持人工离线对比。

**Non-Goals:**

- 不建设完整管理员 CMS、账户体系、多租户管理或用户贡献平台。
- 不实现线上双 Agent、自动分歧协调、自动漂移统计、发布门禁、评估管理后台或重放界面。
- 不实现向量语义检索、语义去重、自动知识卡片合并或完整事件溯源。
- 不提供综合面试或项目深挖、全栈、系统设计、协作责任感等其他独立专项。
- 不评价发音，不优化简历，也不把私人内容自动加入全局评估集。

## Decisions

### 1. 采用小程序薄客户端和模块化单体后端

系统划分为：

- 微信小程序：五栏导航、上传、录音、转写确认、面试轮次、报告和复盘交互。
- 后端 API：身份校验、内容、配置、面试编排、评分、复盘和 Trace 模块。
- 关系数据库：保存领域实体、状态、稳定 ID、版本引用和最小 Trace。
- 对象存储：保存 PDF 简历、JD 图片和待处理的临时音频；私人对象必须按 owner 隔离。
- 后台任务执行器：处理 PDF、OCR、内容导入和可重试的模型调用。
- 本地离线评估运行器：运行人工评估集并生成可人工比较的结果文件。

MVP 使用模块化单体而不是微服务，原因是当前只有一个用户，核心复杂度来自领域关系和 AI 可靠性而非吞吐量。模块边界和稳定 ID 仍需明确，以便以后按需要拆分。外部 LLM、OCR、语音转写和对象存储均通过接口适配器接入，避免设计绑定单一供应商。

### 2. 微信身份采用允许名单，但所有私人数据仍显式归属用户

小程序通过微信登录换取稳定身份标识，后端将其映射到内部 `user_id`。MVP 仅允许配置中的一个微信身份访问；其他身份返回无权限，而不是自动注册。

所有简历、JD、私人内容、面试、评分、卡片和复盘实体必须保存 `owner_user_id`。查询不能依赖“当前只有一个用户”而省略归属条件。这样可以在未来取消允许名单并引入账户体系，而无需重建私人数据关系。

### 3. 平台核心内容通过版本化导入包发布

平台内容不提供运行时编辑后台。管理者在仓库外准备 XMind 或 Markdown，再通过一次性导入命令生成候选内容版本。导入过程分为解析、校验、预览报告和原子发布四步。

XMind 用于建立能力与知识点层级；Markdown 用于补充知识说明、题目、参考答案、评分要点、适用年限、能力标签和知识点绑定。导入器输出不可变的 `content_version`，新面试只读取当前已发布版本，历史面试继续引用原版本。

稳定知识点 ID 不由每次导入时的名称重新计算：

- 首次导入为节点分配稳定 ID，并在导入清单中保存“来源键 → 稳定 ID”映射。
- 后续导入使用来源键延续稳定 ID；节点改名或移动不改变 ID。
- 来源键丢失或发生冲突时，导入失败并生成待人工处理报告，不通过相似名称自动合并。
- 核心题目只能绑定当前内容版本中存在的知识点 ID。

私人知识资料和私人题库仅接收 Markdown。解析后的私人节点使用 `owner_user_id` 隔离；无法可靠映射到平台 ID 的内容分配私人临时 ID。MVP 只做稳定 ID、显式绑定和规范化文本指纹去重，不做向量语义匹配。

### 4. 简历与 JD 采用“当前附件 + 面试快照”

用户最多保存一份当前 PDF 简历。上传新简历会替换当前附件，但不会修改历史面试中的简历解析快照。解析结果包含项目、职责、技术栈和候选人自述能力，仅用于选题与经历核验，不直接参与加减分。

JD 只允许按顺序上传多张图片。OCR 合并结果必须由用户确认；用户可以修正 OCR 文本，但不能绕过图片直接创建纯文本 JD。目标公司是可选参考，系统生成可确认的业务场景摘要，不声称掌握公司内部系统或真实题库。

面试开始时创建不可变配置快照，至少包含：

- PDF 简历解析结果及解析器版本；
- 5～10 年工作年限；
- 目标公司及已确认业务场景；
- JD 图片引用、确认文本及 OCR 版本；
- 语言、时长；
- 平台内容、私人题库、模型、Prompt 和评分规则版本。

### 5. 题目计划使用软覆盖目标和受控候选池

开始面试时，编排器分别构建公共核心/JD、简历技术路线和私人题库候选池。50/30/20 是计划和观测目标，不是强制配额。

选题顺序为：

1. 根据工作年限、AI 应用工程范围、语言和已确认场景过滤候选题。
2. 使用知识点 ID、题目 ID 和规范化文本指纹排除明确重复。
3. 让 LLM 在受控候选 ID 列表中输出题目选择和理由；服务端拒绝不存在的 ID。
4. 当私人题库不足时，允许从平台核心题库或受控 LLM 生成候选中补充。
5. 如果只能通过重复或无关题目满足比例，则接受覆盖不足并记录实际比例。

JD 与公共核心命中同一知识点时只考察一次，并保留多个来源标签。公司场景只改变题目背景和约束，例如库存、履约或流量特征，不替换应考察的核心能力。

### 6. 面试运行显式状态机

面试状态至少包括：

`configured → in_progress → awaiting_transcript_confirmation → scoring_turn → in_progress → finalizing → completed`

并允许进入 `ended_early`、`failed_recoverable` 或 `failed_terminal`。

每轮遵循：

1. 展示主问题或追问；
2. 用户录音；
3. 语音转写并展示不可编辑的确认文本；
4. 用户确认或重新录制；
5. 保存回答、证据和过程评分；
6. 根据证据覆盖、缺口和剩余时间决定追问、切换知识点或结束。

每题最多三次录制。重新录制时删除上一份音频；确认转写后删除最终音频。对象存储同时配置短 TTL 作为删除失败的兜底，但 TTL 不能替代主动删除。三次均因系统原因转写失败时允许跳过或结束，并记录系统失败，不记录候选人短板。

### 7. 单一线上 Agent 分两阶段评分

在线只使用一个面试 Agent：

- 过程阶段：每次回答后输出知识点命中、证据片段、深度、工程应用、评测意识、取舍和候选短板，用于动态追问。
- 最终阶段：面试结束后读取完整确认转录和配置快照，重新校准五维结果并生成唯一的用户可见报告。

Agent 必须输出符合版本化 JSON Schema 的结构化数据。服务端校验枚举、知识点 ID、分值范围、权重和证据引用；校验失败时重试有限次数，仍失败则记录系统失败并保留可恢复状态。

证据引用指向不可变回答文本及字符区间，不能只保存模型生成的摘要。最终五维权重固定为：

- 问题定义与成功指标：15%
- AI 方案与模型应用：25%
- 路线专项能力：20%
- 评测与可靠性：25%
- 工程交付与技术取舍：15%

JD 只能调整维度内部的重点知识点和达标描述，不能修改一级权重。没有足够证据的维度显示“尚未评估”，不得按零分计算。简历只用于提问和核验，不能作为得分证据。

候选人回答暴露的能力缺口进入用户可见短板；OCR、转写、提问、结构化输出或评分链路错误进入内部系统失败。两类失败必须使用不同实体和标签体系。

### 8. 知识映射由服务端约束，低置信度交给用户确认

Agent 只能从当前平台知识点 ID 和本用户私人知识点 ID 列表中选择短板映射，并返回置信度与证据。服务端验证 ID 的版本和归属。

- 高置信度且 ID 有效：作为候选短板展示。
- 低置信度：展示建议映射，由用户确认后才能加入复盘。
- 无匹配：创建私人临时知识点 ID，并标记来源为 AI 推断。

复盘关联优先按知识点 ID 查找已有卡片，不使用语义相似度自动合并。无卡片时由 LLM 生成通用知识卡片，内容与本次个人失败证据分开保存。用户编辑 AI 卡片时保留原始来源和编辑状态。

### 9. 复盘以面试批次为聚合边界

每场面试最多创建一个复盘批次，只有用户明确选择短板并确认后才创建。重复短板在新的面试中生成新的复盘项，但继续关联同一稳定知识点和已有知识卡片。

用户逐项手动标记完成；全部完成后批次自动归档。知识卡片聚合展示累计复盘次数、当前是否待复盘和最近复盘时间，具体问题、回答、遗漏和评分只在对应面试与复盘详情中展示。

### 10. 采用领域表加最小 Trace，而非完整事件溯源

当前状态保存在普通领域表中，关键过程另写入只追加的 `trace_event`。MVP 至少记录：

- `interview.created`
- `question.displayed`
- `transcript.confirmed`
- `assessment.processed`
- `assessment.finalized`
- `review.created`

每条事件包含 `trace_event_id`、`interview_id`、事件类型、发生时间、关联实体 ID、actor、correlation ID、版本引用和结构化 payload。Trace 用于定位证据和比较版本，不承担恢复所有业务状态的职责。

最小领域实体如下：

| 领域 | 核心实体 |
|---|---|
| 身份与文件 | User、StoredAsset、CurrentResume |
| 内容 | ContentVersion、KnowledgeNode、CoreQuestion、PrivateDocument、PrivateQuestion、KnowledgeCard |
| 配置 | ResumeSnapshot、JdSnapshot、InterviewConfigSnapshot |
| 面试 | Interview、InterviewTurn、QuestionInstance、AnswerTranscript |
| 评分 | EvidenceSpan、ProcessAssessment、FinalAssessment、WeaknessCandidate |
| 复盘 | ReviewBatch、ReviewItem |
| 质量 | TraceEvent、SystemFailure、EvalCase、EvalRun |

所有实体使用不依赖数据库顺序的稳定 ID，并保存创建时间、更新时间、owner 和必要的版本引用。历史快照和已确认回答不可被后续编辑覆盖。

### 11. 离线评估是人工运行的第二链路

第二 Agent 不进入线上请求。小型评估集以版本化 Markdown/JSON 样本保存在受控位置，每个样本包含配置、问题、回答、人工期望分数区间、短板标签和证据锚点。LLM 生成的变体必须经人工审核后才能进入固定集合。

离线运行器对同一输入执行当前面试 Agent 的最终评分和第二评估 Agent，输出结构化差异，包括五维分差、等级变化、短板标签、证据引用、延迟和成本。首版由管理者手动查看结果并决定是否采用模型、Prompt 或规则变更，不自动阻止发布，也不提供管理界面。

### 12. 小程序页面围绕最小闭环组织

- 首页：知识卡片流，用户滑动浏览并手动标记已学习。
- 复盘：最近一次复盘置顶，下方展示全部待复盘批次。
- 模拟：中央突出入口，进入配置、面试和结果流程。
- 上传：私人 Markdown 历史、私人知识库和题库入口。
- 我的：当前 PDF 简历、历史分数和基础设置。

复杂导入、离线评估和系统失败排查不进入小程序界面，通过本地工具、数据库查询或结构化输出文件完成。

## Risks / Trade-offs

- [单一 Agent 同时提问和评分可能产生自洽偏差] → 保存过程与最终评分、证据及版本，使用离线第二 Agent 和人工样本定期比较。
- [LLM 输出不稳定或引用不存在的知识点] → 使用受控 ID 列表、结构化 Schema、服务端校验、有限重试和系统失败记录。
- [XMind 节点改名或移动导致知识 ID 漂移] → 使用持久化来源键映射；缺失映射时中止导入并要求人工处理。
- [不使用向量匹配会产生近义重复卡片] → MVP 接受该限制，只通过稳定 ID、显式绑定和文本指纹避免确定性重复。
- [录音主动删除可能因外部服务失败而遗漏] → 删除操作幂等重试、记录删除状态，并设置短 TTL 兜底。
- [小程序请求时限不适合长时间 OCR/LLM 调用] → 使用后台任务与轮询状态，面试轮次使用可恢复状态和幂等请求。
- [单用户实现容易留下全局查询捷径] → 数据库和服务接口从第一版强制传递 `owner_user_id`，自动测试覆盖越权访问。
- [OCR 或转写错误影响评分] → 必须由用户确认转录；系统失败与候选人短板分离，未确认文本不得进入评分。
- [完整 Trace、评估平台被延期后排障能力有限] → 保留稳定 ID、关键事件、版本和证据引用，首版用结构化查询和本地报告排查。

## Migration Plan

1. 建立数据库迁移、对象存储命名空间和唯一允许的微信身份配置。
2. 实现并运行平台内容导入器，发布首个核心内容版本；导入校验失败时不得产生部分发布。
3. 配置 LLM、OCR、语音和文件存储适配器，在非生产环境完成契约测试。
4. 导入小型人工评估集，运行当前版本和离线第二 Agent，人工确认基本评分方向。
5. 发布后端与小程序体验版，仅向允许名单身份开放。
6. 使用完整端到端场景验证上传、面试、评分、复盘、音频删除和 Trace 完整性后开始封闭试用。

回滚时优先回退小程序版本、后端版本、模型/Prompt 配置或当前平台内容版本，不删除已产生的面试、证据和 Trace。数据库迁移采用向前兼容策略；若新字段暂时不用，旧服务应能忽略，而不是通过破坏性回滚丢弃数据。

## Open Questions

- 具体使用哪一家云、LLM、OCR、语音转写和对象存储供应商，可在实现开始时依据成本、地域合规和小程序接入条件选择；适配器边界不变。
- PDF、JD 图片、Markdown 和单次录音的大小上限可根据所选供应商限制确定，不改变核心流程。
